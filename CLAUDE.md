# Bleeders

The game: a third-person narrative RPG/adventure with an orthographic 2.5D look (3D scenes with hand-drawn textures and a 2D feel), point and click, player-paced (no decay timers or forced timings). Lighting is the most important part of the look.

It is built on the FlickerVoid engine (FlickerVoidNGN), one clone of which every project shares, named by the `FLICKERVOID_ENGINE` environment variable. The engine's `CLAUDE.md` describes the stack, the engine modules, the editor and the conventions; read it before working here, as its rules (Arch-first entities, data-driven content, the ontology tree and the rule of three, porting from Unreal, code style, TDD, test builders) apply to this repository too. The plan and roadmap are the engine's `Docs/Plan.md` and `Docs/Port.md`.

## Engine

- `Directory.Build.props` sets `$(FlickerVoidEngine)` to the `FLICKERVOID_ENGINE` environment variable (the build stops when it names no engine) and imports the engine's `Directory.Build.props` and `Directory.Packages.props`. There is never a copy of the engine per project. Projects reference the engine's projects (`$(FlickerVoidEngine)Source/Engine/<Module>/...`), not its packages, so every build compiles the engine. `Bleeders.slnx` lists only the game's projects, as a solution can't read the variable; engine code is edited in the engine's own solution.
- The game builds against whatever the engine clone holds; nothing pins a commit. Engine changes are made and merged in FlickerVoidNGN; a change that spans both lands in the engine first. CI checks the game and the engine out side by side (`.github/workflows/ci.yml`), the engine on its branch of the same name when it has one (a change spanning both uses one branch name in both), else main; the engine's CI builds and tests the game the same way.
- Projects can sit anywhere: the editor's project picker remembers every project it opened (Browse to `Bleeders.fvproject` once).

## Layout

- `Bleeders.fvproject` opens the game in the editor (`game`: `Source/Launcher/Bleeders.Launcher.csproj`; `startupScene`: `Scenes/Main.fvscene`; `splash`: `Splash.jpg`, a neon city under a cut red sun with the title, which the editor shows while it builds the game). `Source/Launcher` runs it on `Content/Scenes/Main.fvscene`.
- `Source/<Module>/Bleeders.<Module>.csproj` (`Gameplay`, `Interface`, `Launcher`), tests in `Tests/<Module>/Bleeders.<Module>.Tests.csproj`, folders following the ontology tree (`Gameplay/Protagonist/Identity/Social`), namespaces following folders. Game-specific rules (social, quests), content and their tests live here, never in the engine; generic systems go to the engine.
- `Source/Gameplay/GameplayModule.cs` is the game's `IGameModule`, registering its components, systems and hooks (with the engine's vehicles, buildings, props and foliage, `AddVehicles`, `AddBuildings`, `AddProps` and `AddFoliage`, so a `vehicle` entity spawns its `.fvvehicle`'s parts, a `building` its `.fvbuilding`'s storeys, stairs, elevator and doors, a `prop` its `.fvprop`'s boxes and doors, and a `foliage` or `foliageScatter` entity its `.fvfoliage`'s plant, once or scattered); `Serialization/BleedersJsonContext.cs` is its source-generated JSON context. The launcher adds the module to `SceneHost.Game` and saves under `FlickerVoid/Bleeders` in the user's local application data.
- Inside the `Bleeders` namespaces, engine types are named in full (`FlickerVoid.Engine.Runtime.Components.Transform`), never as `Engine.…`.

## Game

- Walking to what was clicked is the game's controller's job, over `Characters`: `ClickControlSystem` (`Gameplay/Protagonist/Control`, over the `Player` entity class: protagonist, interactor, mover, transform) turns a press of `Input.Use` into a ray from the camera, walks the `protagonist` there, or focuses the interactable it hit, walks within reach (to the interactable's use point when it has one, `InteractionSystem.GetUsePoint`, so it steps onto an elevator's platform or stands at a door's middle) and presses Use (and ignores clicks while the protagonist is in a conversation), its `InputContextSystem` holds the `Input.Context.Conversation` and `Input.Context.Cutscene` contexts of `Content/Input/Controls.fvdata` while the protagonist talks or a skippable shot plays, so only their actions are read, its `WalkControlSystem` turns the `Input.Move` action (WASD) into a `SteerCommand` on the ground relative to the camera, held still during a conversation, its `InteractableHighlightSystem` outlines the interactables the protagonist's interactor could use within its `interactableHighlight` range (`InteractableHighlight`: range, color) and takes the outline off the rest, as outline requests (`Outline.Highlight`), so an interactable's own outline comes back, and its `DoorSwingSystem` (`Gameplay/World/Objects/Doors`, over the `Door` entity class) swings a `doorSwing` door about its hinge as its toggle changes and rattles it when locked (a `NoiseEvent` from whoever tried it); its `KeySystem` (`Gameplay/Protagonist/Resources/Possessions`) hears a toggle blocked by a lock first and, when whoever was blocked carries an item with the lock's `Key` tag, unlocks it (taking the key when the lock consumes it) and lets the toggle go ahead. The main scene has a cellar key pickup the fox takes before the door opens. Residents (`Gameplay/World/Society/Residents`, in place of the Unreal StateTree AI): a `resident` (wander radius, rest) is run by `ResidentSystem` (over the `Dweller` entity class: resident, state, transform), which faces whom it talks to, stops to watch whom it sees until it loses sight of them, turns toward noises it hears, and otherwise walks to random points within its wander radius of home, resting between walks; the innkeeper watches the fox and turns at the rattling door.
- Driving (`Gameplay/Protagonist/Control`): `DriveControlSystem` puts the protagonist in the nearest vehicle that takes a driver (the engine's `VehicleDriveSystem.CanDrive`: not a trailer) within 3.5 m on `Input.Drive` (E) and lets it out on the vehicle's left on the next press. While it drives it carries `Driving`, is hidden and nested under the vehicle (so the camera on it follows), the vehicle carries the engine's `DrivenVehicle`, `Input.Move` (WASD) is the accelerator and steering relative to the vehicle, pressing against the way it rolls brakes before it reverses, `Input.HandBrake` (Space) holds the hand brake, and walking and clicking are off. `DriveControlSystemTests` drive a new car on a floor.
- The street (`Main.fvscene`, the `Street` folder, greyboxes for now; owner 2026-11-23): the inn (the room as its ground floor, a closed upper storey and a roof), a two-storey house (a door, windows, stairs up through the ceiling) and a shack with a broken roof over a wine cellar (stairs down through its floor, a lantern, the outside muted). Each building is an empty entity with its storeys nested as indoor volumes (dark inside but for windows, holes and lamps) and their pieces nested under them, so the engine's `CutawaySystem` opens the storey the fox stands in. The inn's room model has no walls to walk into, so unseen static bodies (`Inn Wall ...`) close it but for its front entrance. The innkeeper's kinematic body follows it without carving paths, the door's swings with it and paths go around it, and the pickups' bodies leave paths alone (`obstacle: false`). Yellow `doorway` outlines (the `Doorways` folder) mark every entrance and stair head, and the cellar door is `uncut`, so the cutaway never hides it. The `Street` shot tracks the fox along the street, and the `Inn Room Cue` area (an in-out cue, `on: Both`) switches to the room shot on entering and back to `Street` on leaving. `PointerPicker` passes clicks through what the cutaway hides (`CutawaySystem.IsUnseen`). `StreetTests` (`Tests/Gameplay/World/Buildings`) walk the fox out, upstairs and into the cellar, keep the inn open once it stops and keep it inside the inn's walls when steered.
- Materials are instances of the engine's masters and starter instances (`Content/Materials`): the inn's wall on `Surface` (its painting, a little tint variation and damp at its foot), the door, crate, table and mug on the engine's `Wood` and the door's fittings on `Brass`, and the innkeeper's face and hands on `Skin`, each in the model's own colours (tint white). The street shows the masters off: the shack's ground floor fronts are shop windows (`Shop Window`, on the engine's `Dirty Window` glass) between a sill and a lintel, two lamp posts (`Lamp Post`, painted metal, with a bulb head and a warm point light) and a neon sign over the inn (`Sign Board` with pink and cyan `Neon` bars and a pink light); greyboxes take a `material`. `Moods/Dusk.fvmood` reflects the engine's `Venice Sunset` panorama in glossy surfaces. `ContentTests` build the engine's content beside them, so the content check finds the `Engine/` parents.
- The HUD minimap draws the minimap view's markers (the tracked one as a diamond); `Maps/Inn.fvdata` covers the inn, the innkeeper is a `Person` marker and the cellar door an `Objective` shown while the cellar quest is active.
- The launcher quick saves to the `Quick` slot with `Input.QuickSave` (F5) and loads it with `Input.QuickLoad` (F9) before the next tick (`QuickSaves`); its debug interface captures the keyboard while it wants it, and its Rendering panel switches the renderer through the engine's `r.` console variables (`RenderingSettings`), which `Content/Settings.fvsettings` sets when the game starts. The stage 7 gate is the project's `StoryLoopTests` (`Tests/Gameplay/Story`), which travel to the source `Main.fvscene` headless, read the game's controls and play the cellar key quest through clicks and choices, with a save and load in the middle, after a restart and in the same session. `ContentTests` (`Tests/Interface/Content`) run the engine's content check over the game's content.
- The story: the protagonist is the `Player` of `QuestSystem` and `KnowledgeSystem` while it is active (`GameplayModule`), the innkeeper in `Main.fvscene` has a Talk offer (`Interactables/Talk.fvdata`, `startConversation`) and the dialogue `Dialogues/Innkeeper.fvflow`, which gives the cellar key quest (`Quests/Cellar.fvdata`) and a topic (`Knowledge/Cellar.fvdata`). The launcher's debug interface (`--debug` or F1) also has a Story panel (`StoryWindow`: the line, the choices to pick, quests and knowledge).
- The rules: the fox has skills (Perception, Stealth, Charisma) and physical attributes (Health, Intoxication) in `Main.fvscene` and the `Abilities/Protagonist.fvdata` set with `Ability.Lockpick` (needs an `Item.Lockpick`). Its `LockpickSystem` (`Gameplay/World/Objects/Doors`, beside the door) hears a toggle blocked by a pickable lock that no key opened (after `KeySystem`), activates the ability on the door and rolls `Checks/Lockpick.fvdata` (Perception, 2d6, +1 unless `Status.Drunk`) against 4 plus a tenth of the lock's difficulty; success opens it like a key (`DoorLocks.Unlock`), failure cancels the ability and the lock is not picked again until the picker's bonus (the check without its roll) is higher than when it failed (`FailedPick`, saved), and `LockpickedEvent` carries the result. A mug of ale on a crate (`Items/Ale.fvdata`, drunk where it stands) adds Intoxication and the `Drunk` modifier. The launcher's debug interface has a Rules panel (`RulesWindow`: attributes with their bases, modifiers, abilities and the last check).
- The scanner (`Gameplay/Protagonist/Resources/Knowledge/Scanning`, ported from the Unreal scanner for point and click): a `scanner` (range, eye height, line of sight, update interval) on the protagonist and `scannable`s (a `ScanDefinition` data asset, type `scan`: display, category, scan duration, `ScannableWhen`, up to three shown `ScanEntry`s each with `VisibleWhen`, `OnScanned` applied on the first completed scan; and the height the scanner looks at). `ScannerSystem` (a fixed system and service, added where there is a window, as it focuses through `PointerPicker`) turns scan mode on and off with `Input.ScanMode` (F), reveals the scannables within range whose conditions pass, focuses the revealed one under the pointer when the scanner sees it, and scans it while `Input.Scan` (the right button) is held (`ScanModeChangedEvent`, `ScanRevealChangedEvent`, `ScanFocusChangedEvent`, `ScannedEvent`). Scan mode does not slow time (the game is player-paced) and revealed scannables are not yet highlighted in the world. The HUD's scan card (`ScanCardViewModel`) takes the prompt's place in scan mode: the focus's title and progress, then its visible entries. The door, the innkeeper and the ale have scans (`Scans/`).
- The camera direction (`Main.fvscene`, its shots and cue areas in the `Cameras` folder): the `Camera` entity is the starting room shot with the `Cameras/Room.fvdata` rig (a small follow and look, shake, zoom punch); every cue area is one in-out trigger (`on: Both`, with its `exitShot` and `exitTransition`): the `Window Spot` area blends to the `Window` shot and plays it (turning about the room and zooming out) and leaving it blends back; with the key found (`Found.CellarKey`, set by the key's own `Interactables/CellarKey.fvdata` pickup) the `Cellar Stairs Cue` area fades and pushes the low `Cellar` shot at the door, and leaving it returns with a fade; and the cellar quest's flow (`Quests/Cellar.fvflow`) plays the skippable `Key Reveal` cutscene once the key is found (pushed with a cross-fade, played without layers, returned with a blend; `Cutscene.KeyFound` keeps it from playing twice). The `Camera` entity is also the `mainCamera`, naming the lens every shot draws with (`Cameras/Main.fvlens`: no bloom, a soft dark vignette on the paint (`vignetteIntensity` and its radius and softness), a faint warm lens flare (`Cameras/Street.fvflare`: five ghosts, a faint halo tinted warm toward the edge, no glare; `flareIntensity` 0.5 from a threshold of 3), the Uncharted 2 tonemapper, the linen canvas and the depth fade, nearer than the fox darker with a burn on mid-tones, farther losing colour; the haze itself is the environment's: `hazeStart`, `hazeMax`, `hazeDensity`, `hazeColor`, `hazeFromSky` keyed in `Street.fvenv`); the `Cellar` shot's mood (`Cameras/Cellar.fvmood`) darkens the low foreground more while it is live. The street's light over the day is `Environments/Street.fvenv` (the scene's `sceneEnvironment`, held at 18:00 with speed 0, so the game starts as before): ambient, fog, exposure, contrast, saturation and tint keyed at midnight (the old Night mood), noon (Day) and 18:00 (Dusk), edited in the engine's environment editor. The sky step (owner, 2026-11-26) added the sun's and moon's light, the sky's colours and band and the stars to it, keyed at night, noon and dusk; the scene's environment sets latitude 45, north 186 and declination 20.9, so the sun's path puts the 18:00 sun where `Dusk.fvmood` used to hold it, and paints the sky with `Skies/Street.png` (the example painted mask in red and the cloud streaks in green, 2048 by 512, 16-bit, imported as a mask by its `.fvtexture`). `Moods/Dusk.fvmood` keeps the rest. The air (VE report step 2, 2026-11-27): `Street.fvenv` keys the automatic sun beams (`beamIntensity`, strongest at 18:00, a little in the morning, none at night; `beamColor` warm at dawn and dusk), the wine cellar holds a cool low mist (`Cellar Mist`, a `fogVolume` thinning upward) and the inn's room a faint warm smoke (`Inn Smoke`). The fox is the `cameraTarget` and `triggerActivator`. `CameraControlSystem` (`Gameplay/Protagonist/Control`, where there is a window) gives the director the pointer and skips with `Input.Skip` (Space). `CameraDirectionTests` play these on the source scene; the story loop's clicks aim the live shot's drawn view.
- The interface (`Source/Interface`, `Bleeders.Interface`: `InterfaceApplication` with Fluent and `Themes/GameTheme.axaml`, AXAML views over CommunityToolkit.Mvvm view models of the game's services) is drawn by the launcher's `GameUi` under the debug interface (`FrameOverlays`). `GameInterface` (a frame system) owns the HUD (`HudViewModel`, `HudView`): the quest tracker at the top left (`QuestTrackerViewModel`: up to three active quests, the latest changed first, each with its first visible objective not done), the dialogue box at the bottom centre while talking (`DialogueBoxViewModel`: speaker, line, Next, the numbered choices with locked reasons, Leave), and otherwise the prompt for the interactable under the pointer (`InteractionPromptViewModel` over `InteractionSystem.GetOffers(interactor, target)`; the pointer is found by `PointerPicker`, the game service `ClickControlSystem` picks with). Only the dialogue box takes clicks. The look is white and tintable (owner, 2026-11-21: serious, white, tint set in the engine): `HudTint` and the brushes in `GameTheme.axaml`, `HudFrame` panels (`Controls/HudFrame.cs`: a chamfered outline with corner ticks), headings in Glitch Goblin and text in Rajdhani (SIL OFL only; licences beside the fonts in `Assets/Fonts`), and the minimap at the bottom right (`MinimapViewModel`: the compass ring turned against the camera's heading, a tiled map grid moving under the player, the view cone turned by the player's facing, and the markers of `MapSystem.BuildMinimapView`; images in `Assets/Images`). The hub (`HubViewModel`, `HubView`, over the HUD, which hides while it is open) replicates the Unreal hub: a yellow bar with the skewed `FadingStrips` (an opacity mask), the page tabs and Close, and the selected page; `Input.Hub` (Tab) and Close toggle it, `Input.Back` (Escape) closes it and otherwise the game's window (the launcher turns the engine's `CloseOnEscape` off), `Input.NextPage` (E) and `Input.PreviousPage` (Q) switch pages in a ring, and it reopens on the page last shown. While open it pauses the game (`Pause.Hub`; its stage still turns) and holds the `Input.Context.Hub` context. Its dark background takes every click. Its three pages (`HubPageViewModel`: filled from the protagonist when shown, refreshed by their events while shown) are Inventory (`InventoryPageViewModel`: weight and money, a four-column grid of the carried stacks filled up to the inventory's cells, the selected stack with Use and Wear or Take off, and the outfit slots in two columns, `OutfitSlots`; clicking a slot wears the selected stack there when it fits, else selects what is worn there; the protagonist turning on its stage in the middle, `Stages/Protagonist.fvscene`), Character (attributes, the modifiers on them, abilities) and Journal (active quests with their visible objectives, finished quests, knowledge). `DisplayNames` gives the names shown for tags and definitions without a display name.
- Sound (audio step 1, owner 2026-11-27; the engine's `Docs/Modules/Audio.md`): `GameplayModule` adds the engine's audio (`AddAudio`), the fox is the `audioListener` (the protagonist's ears, turned with the camera), and `Content/Sounds` holds `sound` data assets over placeholder files synthesised by a script (kept in the project's shared files, `audio/make_placeholder_sounds.py`; replace a file with a recording of the same name): the cellar door's `doorSwing` names a `rattleSound` and a `swingSound`, which `DoorSwingSystem` asks for on the door (`PlaySoundCommand`) when a lock blocks it and as it starts to swing, the cellar key's pickup plays `KeyPickup` (a `playSound` effect before `pickUp`), the cellar's lantern hums (`soundEmitter`), and the `Street Ambience` entity plays the street's bed on the `Ambience` bus, which the engine dulls while the fox is in an indoor volume. `StreetTests` hear the scene through a null device, quieter inside the inn than on the street. Music and ambience layers come with step 2.
- Localisation (owner, 2026-11-27: every line of text goes through a key; the engine's `Docs/Modules/Localisation.md`): the game's content writes every player-visible text as a `LocalizedText` (`{ "key": "Quest.Cellar.Name", "text": "The cellar key", "note": "context for the translator" }`), with keys named by kind and file (`Item.Ale.Name`, `Dialogue.Innkeeper.Greet`, `Scan.Door.Lock`); the interface's own fixed labels are `InterfaceTexts` (`Bleeders.Interface.Localization`, declared to the localizer by `InterfaceModule`) shown through `InterfaceLabels` and the page and HUD view models, which turn each text into the chosen language (`Game.Localization`, the `loc.Culture` console variable) as they build and again when it changes. Translations are `.fvstrings` files in `Content/Localization` (none yet; the languages come when the story is further along). `ContentTests` fail on a text without a key or one key given to two texts. The debug windows show texts as written.

## Build and test

- `dotnet build Bleeders.slnx` and `dotnet test --solution Bleeders.slnx` (Microsoft Testing Platform, xUnit v3), from the repository's root, which has its own `global.json`.
- CI (`.github/workflows/ci.yml`) checks out the engine and builds and tests on Windows and Linux for every pull request and push to main.

## Git

- Branches: `feature/<title>`, `improvement/<title>` or `bug/<title>`, the title saying what the work does.
- PRs open ready for review; the owner reviews and may push to the branch.
